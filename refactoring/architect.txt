АРХИТЕКТУРНЫЙ ОТЧЁТ ПО РЕФАКТОРИНГУ
Проект: fff (NestJS + Prisma/SQLite + React/Vite + nginx)
Дата анализа: 2026-11-16
Статус: анализ исходников и конфигурации завершён; изменения в runtime-код не вносились.
Решение текущего цикла: scope ограничен безопасным clean-code/refactoring без изменения auth-семантики, схемы/миграций Prisma, status transitions и nginx-контракта; последующая проверка выполняется QA.

1. РЕЗЮМЕ
Система представляет собой небольшой Kanban: NestJS API с глобальным префиксом /api, Prisma-моделью Task в SQLite, React/Vite UI с @dnd-kit и nginx перед frontend/backend. Код компилируется: backend `nest build` и frontend `vite build` успешно завершены. Frontend build выдаёт предупреждение о крупном JS-чанке (~1.03 MB, ~330 KB gzip).

Сильные стороны:
- DTO и глобальный ValidationPipe включают whitelist, transform и forbidNonWhitelisted.
- Prisma доступен через отдельный модуль/сервис, операции перемещения используют транзакцию.
- Статусы и приоритеты централизованы в task-status.ts и повторно валидируются DTO.
- Frontend имеет optimistic update с откатом при ошибке drag-and-drop.
- nginx закрывает весь внешний контур Basic Auth, backend также проверяет token header.

Ключевые риски:
- Авторизация реализована единым статическим токеном в x-access-token и передаётся во frontend через VITE_TOKEN; это секрет, фактически попадающий в браузерный bundle. Не менять контракт без отдельного решения: миграция может сломать клиентов.
- Если TOKEN не задан, middleware пропускает все запросы (fail-open). Для production это критический риск конфигурации.
- Нет тестов, health/readiness endpoint, structured logging, централизованной обработки ошибок и наблюдаемости.
- Строковые status/priority в Prisma допускают несогласованные значения; часть бизнес-логики делает casts без runtime-защиты.
- Перемещение нормализует позиции циклом отдельных UPDATE внутри транзакции; при конкурентных запросах возможны блокировки/гонки, а операции O(n).
- SQLite и `prisma db push` в docker-compose подходят для разработки, но не для управляемой production-митигации.
- nginx proxy для `/api/` не задаёт явно timeout/лимиты/заголовки безопасности; Basic Auth и token одновременно создают двойной контур доступа.
- App.tsx содержит состояние, загрузку, DnD, CRUD и страницы настроек (~471 строка), затрудняя изолированное тестирование.

2. ФАКТИЧЕСКАЯ АРХИТЕКТУРА
Backend:
- `backend/src/main.ts`: bootstrap, `/api`, token middleware, CORS, ValidationPipe, listen.
- `AppModule`: ServeStaticModule обслуживает `frontend/dist`, PrismaModule, TasksModule.
- `TasksController`: list/backlog/archived, create/update/delete, move/archive/restore.
- `TasksService`: queries, создание, update, перемещение и нормализация order.
- Prisma schema: Task(id, title, description, status, priority, color, order, timestamps, dueDate), индекс(status, order).
Frontend:
- `api.ts`: типизированные fetch-обёртки, x-access-token из VITE_TOKEN.
- `App.tsx`: три набора задач, вкладки, optimistic drag, модальная форма, theme/localStorage.
- `TaskCard`, `KanbanColumn`, `TaskModal`: UI и DnD.
Infrastructure:
- docker-compose поднимает Node dev-контейнеры с `npm install`, `prisma db push`, hot reload.
- nginx слушает 80, Basic Auth, проксирует `/api/` на backend:3000 и `/` на frontend:8000.

3. АВТОРИЗАЦИЯ — СОХРАНИТЬ TOKEN-BASED КОНТРАКТ
Текущий контракт: backend принимает `x-access-token`; значение сравнивается с `process.env.TOKEN`. Frontend отправляет `VITE_TOKEN`. Этот контракт не следует менять в рамках чистого рефакторинга.

Безопасные улучшения без смены схемы:
1) Не логировать токен; добавить маскирование чувствительных заголовков в логах.
2) При production-конфигурации требовать TOKEN (fail-closed): приложение не стартует или API отвечает 503 при отсутствии секрета. Обсудить отдельно, поскольку dev без TOKEN сейчас открыт.
3) Сравнивать токены constant-time (crypto.timingSafeEqual) после проверки одинаковой длины; сохраняется header и формат.
4) Ввести отдельную Nest guard/middleware с тестами вместо анонимной функции в main.ts; поведение status 401 и имя заголовка сохранить.
5) Проверить, действительно ли frontend должен знать token. В краткосрочном периоде VITE_TOKEN оставить; долгосрочно предпочтительно server-side BFF/httpOnly cookie или nginx injection, но это уже миграция авторизации и не входит в безопасный рефакторинг.
6) Согласовать Basic Auth nginx и token: документировать, что nginx защищает внешний perimeter, token защищает API; не удалять ни один механизм без threat model.

5. ЧИСТЫЙ КОД И КОРРЕКТНОСТЬ
Высокий приоритет:
- Разбить однострочные методы TasksService на читаемые функции; убрать неиспользуемые импорты TASK_PRIORITIES/TaskPriority.
- Использовать Prisma enum для status/priority либо domain mapping + DB CHECK; сейчас String допускает мусор.
- Явно разрешить переходы статусов (например, archive/restore/move), а не принимать любой статус из одного DTO. Зафиксировать бизнес-правила.
- Валидация дат: DTO принимает ISO, но сервис делает `new Date` без проверки Invalid Date; добавить IsDateString уже есть, затем проверять timezone/диапазон и нормализовать UTC.
- В `create` статус BACKLOG/ARCHIVED допустим, count-based order может быть некорректен при удалённых gaps; добавить единый order service.
- `move`: проверить существование/валидность target status, запретить неожиданные перемещения, обеспечить уникальность/детерминизм `(status, order)` при конкуренции; рассмотреть fractional rank или bulk update.
- Endpoint `PATCH /tasks/reorder` использует id в body, тогда как `/move` использует path id; оставить для обратной совместимости, документировать deprecation.
- Возвращать DTO/serializer, а не Prisma entity напрямую; не допустить будущего раскрытия внутренних полей.
- Добавить pagination/limit для list endpoints, особенно archived.
- Error responses привести к единому формату (код, message, requestId).

Frontend:
- Вынести из App.tsx загрузку и mutations в hook; разделить tabs/pages и статистику.
- Не мутировать результат `.sort()` после `.filter()` безопасно сейчас, но перейти к memoized selectors.
- Исправить тему: Root фиксирует dark initial state, App отдельно изменяет state; ConfigProvider может не переключаться после клика. Поднять theme state в единственный provider.
- Настройки dueDays/overdueColor сейчас только local React state и не используются для overdueColor; либо реализовать persistence/API, либо убрать неподдержанные controls.
- `TaskCard` вызывает useSortable и для архивных/overlay карточек; отделить draggable и display варианты.
- Добавить ErrorBoundary, retry/loading empty states, AbortController для unmount/race.
- API-клиент должен безопасно обрабатывать 204, JSON/non-JSON ошибки и 401 (явное сообщение/redirect).
- Снизить bundle: code-split Ant Design/страницы, проверить source map и chunk limit; не принимать warning как blocker, но измерять budget.
- Уточнить Vite env naming: `CREATED_CARD_COLOR`, `BACKLOG_CARD_COLOR`, `ARCHIVED_CARD_COLOR` не имеют VITE_ префикса и в стандартном Vite не попадут в `import.meta.env`; фактически используются fallback. Переименовать после согласования конфигурации.

7. ДАННЫЕ, DEPLOY И ОПЕРАЦИОННЫЕ РИСКИ
- `DATABASE_URL=file:./prisma/kanban.db` в compose относителен к Prisma schema/working dir; проверить фактический путь и volume. Сейчас DB не вынесена отдельным persistent volume.
- Не выполнять `prisma db push` при каждом старте production; использовать committed migrations и `prisma migrate deploy` в release step.
- Закрепить версии Node/package manager и использовать lockfile; compose сейчас запускает `npm install`, хотя repo содержит pnpm-lock.
- Добавить healthchecks и `depends_on` condition: service_started не означает readiness.
- Запускать контейнеры non-root, read-only FS где возможно, ограничить ресурсы.
- nginx: security headers, client body size, proxy timeouts, upstream health, access/error log policy, real IP trust. Не доверять X-Forwarded-* без настроенной trusted proxy.
- CORS allowlist уже есть, но production default localhost опасен; конфиг должен быть явным.
- Secrets `.htpasswd` и TOKEN не должны попадать в git/image/logs; использовать Docker secrets/secret manager.
- Принять стратегию SQLite backup/restore и locking или план миграции PostgreSQL при многопользовательской нагрузке.

9. СПОРНЫЕ РЕШЕНИЯ ДЛЯ ЯВНОГО ОБСУЖДЕНИЯ
A. Fail-open или fail-closed при отсутствии TOKEN? Рекомендация: fail-closed в production, permissive только явно в development.
B. Оставлять VITE_TOKEN в браузерном bundle? Краткосрочно сохранить совместимость; долгосрочно заменить на BFF/httpOnly cookie или иной server-mediated token, так как клиентский секрет не является секретом.
C. Сохранять nginx Basic Auth вместе с token? Рекомендация: пока да (defense-in-depth), но документировать ownership и UX; возможно один слой будет удалён после threat model.
D. Prisma String или enum/DB CHECK? Рекомендация: enum/domain validation + migration; риск обратной совместимости со старыми значениями.
E. Разрешать ли любые переходы статусов через PATCH? Рекомендация: явная state machine; потребуется согласование UX (например, restore всегда DONE).
F. Оставаться на SQLite или перейти PostgreSQL? SQLite достаточен для single-instance/low concurrency; PostgreSQL предпочтителен при нескольких пользователях/репликах.
G. `prisma db push` в compose или migrations? Рекомендация migrations для stage/prod, db push только disposable dev.
H. Где хранить настройки dueDays/overdueColor? Сейчас UI-only и частично неиспользуемы; выбрать localStorage, server settings или удалить controls.
I. Нужен ли `/api/reorder` legacy endpoint? Рекомендация сохранить на период deprecation, затем удалить после telemetry/поиска клиентов.
J. Bundle warning: принять, code-split или заменить UI library? Рекомендация сначала code-split и budget, не переписывать UI без измерений.

10. СОГЛАСОВАННЫЕ КОМПРОМИССЫ И SCOPE ТЕКУЩЕГО ЦИКЛА
Решения Lead, принятые для текущего цикла:
- Сохранить без изменений публичный `x-access-token` header, сравнение с `TOKEN`, включая текущую fail-open семантику при unset TOKEN, и frontend `VITE_TOKEN`.
- Сохранить nginx Basic Auth и его текущий perimeter-контур; nginx-конфигурацию, маршрутизацию и публичные порты compose не менять.
- Не мигрировать Prisma/DB: оставить Prisma `String` для status/priority, SQLite и `prisma db push` в compose.
- Не менять свободные status transitions и не удалять/переименовывать legacy `PATCH /tasks/reorder`.
- Не менять API paths, payload/response contract, CORS/auth behavior или deployment ports.

Разрешённые изменения (без изменения публичного поведения):
- Backend: читаемый/разбитый TasksService, безопасная whitespace-only rejection в DTO (пробелы не должны проходить как содержательное title/description), nullish-safe DTO/reorder handling, typed helpers и локальные unit tests.
- Frontend: API client с корректными 204, 401, JSON/non-JSON error handling при сохранении URL, headers и payload; безопасная очистка/унификация theme state без изменения UX-контракта и token handling.
- QA: typecheck/build, существующие smoke checks и тесты на сохранение token/header, DTO validation, CRUD/reorder compatibility, API error cases и theme behavior.

Обязательные компромиссы:
1) Fail-open при unset TOKEN остаётся осознанным compatibility trade-off, а не исправлением безопасности. Риск (открытый API при ошибочной конфигурации) должен быть явно отмечен в документации и покрыт regression-тестом/QA-проверкой; production hardening вынесен в отдельное решение.
2) `VITE_TOKEN` остаётся доступным в браузерном bundle, потому что изменение на BFF/httpOnly cookie нарушило бы текущий контракт; секретность browser-delivered token не предполагается.
3) Prisma String, db push, SQLite, свободные переходы и legacy reorder сохраняются ради отсутствия миграций и обратной совместимости; целостность/конкурентность и state machine остаются известными follow-up рисками.
4) Nginx Basic Auth, compose ports и proxy behavior не меняются, поэтому operational/security hardening (headers, limits, healthchecks, non-root, trusted proxy) не является частью этого цикла.
5) Clean-code изменения не должны «исправлять» публичные странности (например, semantics restore/archive, response shape или error status) без отдельного согласования; сначала фиксируем поведение тестами.

Out of scope текущего цикла:
- Любая смена auth-семантики, заголовка, TOKEN/VITE_TOKEN, fail-open/fail-closed, Basic Auth или схемы доставки секрета.
- Prisma migrations, enum/CHECK, смена SQLite/PostgreSQL, изменение DB schema/indexes и замена `db push`.
- Изменение status transition policy, order algorithm/concurrency model или удаление/rework legacy reorder endpoint.
- Изменение nginx, compose ports, публичных маршрутов, CORS policy и deployment topology.
- Новые health/readiness endpoints, pagination, serializer/API versioning, BFF, rate limiting, security headers и observability platform.
- Крупная frontend-реорганизация, смена UI library, code-splitting как обязательное требование и изменение visual/product behavior.

Исходники и конфигурация просмотрены; runtime-код не изменён. Сборки backend/frontend прошли успешно через bundled pnpm; frontend сообщил только chunk-size warning. Полноценные unit/e2e тесты отсутствуют в репозитории и не запускались. Авторизация проверена статически по коду, без запуска внешнего nginx и production secrets.
